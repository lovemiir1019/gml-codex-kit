# GameMakerプロジェクトの編集

## 既存の構成を読む

`.gml` はコード、`.yy` は個々のリソースの定義、`.yyp` はプロジェクトの構成を持つ。
`.yy` / `.yyp` は版によって形式が異なり、末尾カンマを含む場合もある。厳密なJSONとして読み直して全ファイルを書き換える方法を、無条件に使わない。
文字コード、改行、識別子、リソースの参照、フォルダ構成、並び順を保つ。無関係な整形を同時にしない。

対象イベントの登録をオブジェクトの `.yy` で確認し、実際の `.gml` と対応させる。
親オブジェクトや関連スクリプトも必要な範囲で読む。ファイル名だけでイベントの意図を決めない。
新しい `.gml` を置くだけでは、オブジェクトやイベントの登録が済むとは限らない。

## 小さな修正と新しいリソースを扱う

既存イベントの修正は対象の `.gml` を中心に行う。書き込み直前に現在の内容を確認し、別の人やIDEによる変更を上書きしない。
新しいオブジェクト、イベント、ルームへの配置には、対応するメタデータも必要になる。
接続済みの公式ResourceToolや、プロジェクトで採用済みのツールが対応していれば利用する。
手動で編集する場合は同じプロジェクト・同じ資産種類の実例と対象版を確認する。形式を確認できない新規資産は、GameMaker IDEでの作成・登録手順を渡し、コードを用意する。

IDEで未保存の内容と外部編集が衝突しそうな場合は、利用者に保存・再読み込みの必要を短く伝える。
スキル導入を理由にゲームの全体構造、出力先、既存の拡張機能を変更しない。

## ビルドと確認

まずリポジトリにある既存のビルド手順を使う。公式gm-cliを利用できる場合も、プロジェクトのRuntimeと出力先を合わせる。
ツールを初めて導入する場合は、必要性・配布元・追加設定を示す。別のAIクライアントすべてへ自動設定する導入を、既定の手順にしない。
GameMakerや必要なRuntimeがない場合、ソース確認と手動確認手順までを行う。成功したビルド、起動、操作確認をそれぞれ実際に行った範囲で報告する。
課金、商用ライセンスの購入、ゲームの外部公開は、通常のコード修正に含めない。
